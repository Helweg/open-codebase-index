There is no paired answer-quality observation for this follow-up and no evidence that the new guard-tracing guidance improved or harmed answers. The runner reported this cell as `missing-final`; that label alone did not identify the failure boundary. Subsequent isolated diagnostics identified the cause: the runner set `XDG_DATA_HOME` to each profile's `xdg-data` directory but verified an authentication file under `HOME/.local/share/opencode/auth.json`. OpenCode looked for credentials under `XDG_DATA_HOME/opencode/auth.json`, found none, and its debug log identified the underlying `ProviderModelNotFoundError` for `opencode-go/deepseek-v4.1-flash`. The failed profile's `opencode auth list` showed zero credentials, and its model catalog contained only unauthenticated free models. In a separate disposable profile, placing a known-working private credential at the effective XDG data path made the Go model discoverable and a neutral `AUTH_OK` request return successfully. Credential contents were not inspected or recorded.

This fixes the **diagnosed setup error**, not the unmeasured answer-quality result. Keep the original follow-up incomplete rather than scoring the parent as a failure. Any comparison must be a distinct, separately frozen study with both arm profiles checking the effective XDG authentication path and passing a non-task authorization smoke. Do not restart the failed cell under this study's zero-retry protocol.

### September 27 post-run correction: plugin exposure and hint lifetime

A subsequent read-only source investigation and fresh, owner-only localhost serialization probe corrected the earlier claim that v7 loaded the intended plugins. Its configured plugin origins and equal 13-tool inventories were not exposure evidence: the inventories contained only built-in tools, with no OCBI tools. In the fresh probe, the actual compiled OpenCode 1.18.32 host failed to import the unchanged staged `675300c` loose-dist entrypoint with `Cannot find package 'zod'`. A standalone Bun import had succeeded, so that smoke did not establish dependency resolution inside the compiled host. This demonstrates a staging/dependency defect in the reproduced loose-dist setup, not the certain cause of the earlier exit-0 incomplete session.

The same neutral two-request probe then used actual npm-packed, clean-installed roots pinned to baseline `675300c` and answer-guidance-lifetime candidate `be26a130`. Both exposed 20 OCBI tools plus 10 built-ins, with identical serialized tool definitions. Actual `index_status` results were also identical: the copied `675300c` branch catalog was ready, with 6,771 active chunks and compatible Ollama/`nomic-embed-text` configuration. Both initial model payloads contained full-path/supporting-line and guard/failure guidance. After the scripted `index_status` call, baseline `675300c` omitted both discovery routing and answer guidance, whereas candidate `be26a130` retained the answer guidance and omitted only the one-shot discovery routing. The endpoint returned fixed local responses, with no external model inference.

These captures establish plugin loading and the intended per-request guidance-lifetime difference for this neutral probe. They do not establish better answers, citation accuracy, or the cause of the old incomplete session. They do not revise the September 25 eight-cell result, its 33-tool preflight, any frozen artifacts or grades, or the historical 2,415-test counts above. Detailed neutral captures and installed-package pins remain in owner-only probe artifacts; any new answer-quality study requires a separate prospective protocol.
