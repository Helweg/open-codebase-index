# Exploratory cross-repository agent task, 2026-09-24

This is **one paired task**, not a claim that OCBI improves agent performance or is state of the art. It asks for a source-cited analysis of github-reviewer's exact-SHA PR preparation and the OCBI provider's authoritative-base handling when `gh pr view` fails, including a stipulated post-materialization ref race. The task genuinely crosses a package boundary: github-reviewer at `6a9604e63509a03efa62b38a0135a5bf5d8633f6` pins `open-codebase-index@0.25.0`, matching provider source tag `v0.25.0` at `f5d186496167273cf06bff43375b108bfaaa7545`. The **retrieval treatment** nevertheless used the latest published OpenCode plugin available for this pilot, `open-codebase-index@0.32.1`; the older pinned source was the object of analysis, not the installed treatment. An independent review checked the relevant behavior in the reviewer's installed 0.25.0 CLI, but did not cryptographically prove tarball/source identity.

## Frozen protocol

The rubric-free solver prompt SHA-256 was `b483a028278a38c75f59a6885d85ad3307751ca7ad247c0043304c797d29d2ff`; the independently reviewed private 12-point rubric SHA-256 was `cf16bbadaea1eb540330e665a8215cb0f5a83307c4d26d7873ba57c520e6dfa8`. The manifest SHA-256 was `5abc03054e3592334d29977fcfc660ff5bb429555cb5e4e427c4c1281c2b73ba`, with seed `exact-pr-base-v1-20260924`. These were fixed before solver exposure. The prompt and key were separately stored outside the trial workspaces. The visible earlier pilot concerned risk-text preservation, not this exact-SHA/base-precedence question; private holdout novelty cannot be established.

Both arms used OpenCode 1.18.32's default `build` agent, OpenCode Go `deepseek-v4.1-flash`, the same frozen prompt, pinned disposable clones under a private `/Users/Shared` root, isolated HOME/XDG/config, and identical prebuilt local Ollama `nomic-embed-text` indexes. Preparation was outside measured agent time. The only intended agent capability difference was registration of published OCBI 0.32.1 in treatment. Same-process preflight verified control had no OCBI tool and treatment exposed its search/status tools; separate CLI status/retrieval confirmed ready indexes for both pinned repos (2,604 provider chunks and 207 reviewer chunks). The runner's declared token/tool limits are not independently enforced by this OpenCode adapter; each agent had a 600-second wall limit. A presence-and-clean-Git verifier checked bounded final answers and no source edits, **not factual correctness**.

The first attempt was killed by the outer command envelope at 600 seconds before a paired result was serialized. Its partial artifact is excluded. The unchanged inputs ran detached in run 2: both presence verifiers passed, but default metadata-only cleanup removed the answer files, preventing blind grading. This is an evidence-retention limitation, not a quality result. Run 3 repeated the same frozen inputs with explicit owner-only audit capture (0700 directory, 0600 files); both agent stdout streams were untruncated. Only final assistant text was copied to neutral-ID files. Two graders verified the rubric hash, independently reviewed pinned source citations without seeing arm labels, and scored before the mapping was unsealed.

## Observations from graded run 3

| Arm | Independent blind grades | Agent duration | Emitted tool-use events | OCBI tool-use events |
| --- | ---: | ---: | ---: | ---: |
| Default OpenCode | 10/12, 10/12 | 137.9 s | 25 other | 0 |
| Default plus published OCBI 0.32.1 | 10/12, 11/12 | 122.2 s | 34 other | 0 |

Both answers correctly covered most source paths but had qualification/citation errors. Graders agreed that the control answer overstated `gh` head equality and miscited the OpenCode rather than MCP error handler. They differed by one point on the treatment answer, which under-specified some `gh` metadata checks and phrased conditional State A success too categorically. Neither triggered the rubric's critical caps. Both presence verifiers returned success, yielding one concordant pair, zero discordant pairs and an exact sign-test p-value of 1 for **answer presence only**. The 10 versus 10/11 blind scores from a single task are not an inferential benefit. Neither treatment run 2 nor run 3 emitted an OCBI tool call, despite registration, so the observed answer cannot be attributed to OCBI retrieval. Duration differences from a single pair are not speed evidence. The adapter did not retain provider token/cost accounting for these trials.

## Follow-up boundary

Separately from this published-version comparison, source commits `f2c666f` and `062b5ff` fix prompt classification and OpenCode title-generation consumption of a routing hint. A real OpenCode localhost request capture confirmed the repaired hint reached the default agent. One **unpaired exploratory** session using that locally built source plugin called `codebase_context` first and got relevant source locations, then used built-in tools; it was not graded as a causal improvement. Neither source fix was in published 0.32.1 used above. A future, preregistered multi-task comparison with the released fix, independently graded harder and diverse questions, and observed actual OCBI use is needed before making a SOTA or effectiveness claim.
