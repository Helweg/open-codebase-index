# Exploratory v0.32.2 cross-repository comprehension study, 2026-09-24

**Result: no causal OCBI gain established.** Four preregistered paired tasks compared OpenCode 1.18.32's default `build` agent and `opencode-go/deepseek-v4.1-flash` with the same agent plus a locally built OCBI v0.32.2 release candidate. One VS Code/ripgrep task favored treatment on blind accuracy, one was essentially tied, and both Next.js/Chakra tasks produced no answer in either arm. Crucially, **neither completed treatment task invoked an OCBI tool**. The observed score difference cannot be attributed to retrieval.

## What the failure taught us

The candidate exposed working indexed retrieval but the OpenCode agent chose built-in `bash`, `read`, `glob`, and `grep` instead. Read-only diagnosis found that every frozen explanatory task was classified as an *external lookup* because incidental words such as `npm`, `package`, `crate`, or `framework` triggered the external-first heuristic. After removing those false positives, incidental file paths and build/test terms still suppressed conceptual routing. Commit `b2674f1` on local main and cherry-pick `07fe75c` on the separate release candidate correct this **eligibility** defect with generic source-grounded tests and explicit external/direct-path negatives. That later fix was **not** present in the graded candidate and cannot retroactively change these outcomes. In a subsequent localhost-only OpenCode 1.18.32 request capture of the updated release candidate, the main agent's serialized system message contained the dynamic fallback hint to check `index_status` and use `codebase_context`; the `codebase_context` tool schema was also present. The capture worktree inherited a compatible shared index, but its `release/v0.32.2` branch had no registered catalog (`indexed=false`, branch readiness `missing`), so this was the bootstrap form of the hint, not the indexed `prefer codebase_context` form. The capture returned an intentional local error and measured neither agent uptake nor answer quality. A separate private, indexed VS Code/ripgrep copy passed both-repository CLI searches and exposed the sole release plugin's tool names, but its one authorized Go request failed upstream with HTTP 401 before any tool call (zero tokens, zero reported cost). A plugin initialization warning also prevented confirming tool execution in that session. Consequently current-release OCBI uptake was unverified **at that stage**. Tool eligibility or use alone still could not establish answer-quality benefit; see the later corrected-adapter rerun below.

No release was pushed, tagged or published by this study. Protected transcripts, source paths and grader mapping remain in owner-only local artifacts, not in this report.

## Corrected-adapter exploratory rerun (later on 2026-09-24)

The earlier 401 did **not** require changing the user's subscription or resetting credentials. A fresh isolated, response-only OpenCode Go request using the same existing `go-private` profile returned `PROFILE_OK` in 4.1 seconds. The failure was session-specific; the cause of the earlier 401 was not proven. The corrected asynchronous adapter also completed a real OpenCode 1.18.32 Go request in 7.9 seconds, and a disposable indexed VS Code/ripgrep session invoked `codebase_context` successfully before `read`. These are real public-host checks, not an answer-quality claim.

A separate four-task rerun then used the same pinned source checkouts, prompts, rubric, scope, and model with a new artifact directory, seed, and **both arms** on the corrected async adapter. Its release-candidate bundle SHA-256 was `c1502ead6b098a96264347f0166047f3a47fcce9e96812796bd4887309056e45`; the new adapter hash was `aa0cc2e31f6fbcec69f66bebc652b832fb148e18839a5c3ea8bd2d78ec7be6d2`. A separate protocol was written before this rerun. It is **exploratory after seeing the earlier outcomes**, not independent confirmatory evidence. The old study and its adapter remain unchanged.

All eight arms completed with untruncated final answers and passed the presence/cleanliness verifier. Two graders blind to arm assignments independently checked the same frozen source-backed rubric; their scores differed by at most one point per answer, no critical caps applied, and scores were recorded before arm mapping was revealed. At the >=9/12 quality threshold, **both arms succeeded on all four tasks**, zero discordant pairs, exact two-sided sign-test p = 1. Average treatment quality was slightly lower (by 0.5 and 1.0 rubric points across the two graders), not higher. The VS Code/ripgrep pair hit a 12/12 ceiling in both arms. Only one of four treatment sessions actually used OCBI, so the rerun still does not demonstrate a retrieval-caused accuracy gain.

Agent execution summed to about 20.9 minutes and $0.1886 reported model cost for treatment versus 23.9 minutes and $0.1590 for control. Four local Ollama treatment index preparations added about 17.2 minutes in total, excluded from those agent times; their energy cost is not measured. Declared 60-tool-call and 12,000-token controls were not enforced by OpenCode: some arms exceeded them. These four correlated, previously seen tasks are too few for a superiority claim. The corrected adapter did eliminate the old symmetric no-answer failure in this rerun, but tool uptake and measurable answer-quality benefit remain separate, unsolved goals. No release was pushed, tagged or published.
